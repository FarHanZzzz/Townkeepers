# Amader TOWNHALL | Technical requirements

Implementation baseline 1.0 · Python · Django · FastAPI · PostgreSQL

Use this file to make implementation decisions against the product behaviors in `GRAND_PRD.md`. Requirement identifiers in that file also identify the acceptance criteria for this design. **Architecture decision:** one repository, one owner of business state, one private assistance API and one PostgreSQL database. Django renders the full browser application. This implements the requested Python stack and supersedes the provisional stack in the earlier SRS §2.3.

## 1. Runtime architecture

| Component | Responsibility | How to verify it |
|---|---|---|
| Browser and Django web application | Same-origin HTML, accessible forms, sessions, Google callback, dashboard, commands, file downloads and exports. Use server-rendered Django templates and CSS. Add browser JavaScript only for interactions that benefit from it. | Complete sign-in, memo, booking and evidence review through their ordinary UI. Server validation still runs when browser checks are bypassed. |
| Django domain modules | Identity and club scope, finance, memo, venue/events, publication, analytics and shared audit/outbox. Each command owns its authorization, validation, transaction and resulting events. | Call a command both from the web view and a test. Both enforce the same policy and produce one result. |
| Private FastAPI service | Accept minimal, schema-validated requests for scheduling recommendations, priority suggestions and OCR. Return typed candidates or extracted suggestions. Django owns all approval, posting, publishing and reservation decisions. | Test the HTTP contract, malformed responses, timeouts and stale results. Run core workflows with the service stopped. |
| PostgreSQL | Authoritative application records, constraints, revision history, job state and transaction boundaries. Django migrations are the schema owner. | Initialize an empty PostgreSQL database, upgrade a populated one, and run integrity and race tests on both. |
| Private file storage | Immutable receipt originals, memo attachments, signed evidence and completed exports. PostgreSQL stores ownership, version, key, digest and review status. A private volume is sufficient in local development. | Deny direct and stale links. Retrieve an authorized original after restore and verify its checksum. |
| Python worker | Django management command polls durable PostgreSQL jobs for IUB email, OCR, publication synchronization and longer exports. Share the project’s domain code. A broker is optional if measured load later requires one. | Stop a worker after claiming a job, restart it, and recover the operation without a second official action. |

Suggested repository layout is `manage.py`, `config/`, `apps/{accounts,clubs,finance,memos,events,publishing,analytics,platform_core}/`, `assistance/`, `templates/`, `static/` and `tests/`. Put scheduling and priority validation in their owning Django domain. Keep provider clients under `assistance/`. Deploy the Django web process, worker and FastAPI process from a pinned Python environment. Route the public origin to Django. Restrict FastAPI ingress to the application network and authenticate service calls. FastAPI receives neither browser cookies nor write credentials for the business database.

## 2. Interfaces and contracts

Django form commands use POST, CSRF protection and a success redirect to a scoped detail page. GET reads official state without changing it. The endpoints below specify the required behavior at representative boundaries. Other screens use the same conventions. Use stable record IDs in URLs and resolve the permitted record on every request.

| Method and route | Required input | Successful result | Rejected or uncertain result |
|---|---|---|---|
| GET /auth/google/start and GET /auth/google/callback | One-time session-bound state and nonce, registered redirect, provider response | Verified institutional identity matched to one active profile, rotated session, permitted dashboard | Generic sign-in failure, fresh attempt, no authenticated session |
| POST /memos/{id}/decisions | Expected memo version, stage, decision, signature for confirmation/approval or reason for rejection, command key | One decision with actor and timestamp, authoritative new stage and required notifications | Stale stage/version shows the current decision. Missing signature/reason identifies the field. |
| POST /bookings/{id}/confirm | Expected revision, current reviewer, command key | One confirmed reservation and corresponding booking decision | Overlap or changed restrictions keep the request unconfirmed and identify the applicable conflict |
| POST /expenses/{id}/verify | Expected expense revision, linked evidence, reviewed values, command key | One verified entry reflected in scoped totals | Ineligible evidence or stale revision leaves the previous balance and state intact |
| POST /events/{id}/publications | Destination, approved event version, reviewed preview version, command key | Internal notice committed or external operation accepted for delivery | Changed version requires a new preview. A queued external attempt is displayed as pending. |
| GET /files/{id} and GET /exports/{id} | Current session and applicable record/export permission | Scoped bytes or an authorized download through a protected proxy | Denied or unavailable response without revealing another club’s file or storage key |
| POST /internal/v1/scheduling/suggest | Permitted candidate IDs, intervals, capacity, duration, preferences and request ID | Candidate IDs drawn from the input, order and concise reasons | Invalid/expired results dropped, manual search available |
| POST /internal/v1/priority/suggest | Opaque queue IDs, relevant dates, review window and permitted policy inputs | Ordered candidates, explanation, calculation time and input revision | Earliest-deadline-first order and explicit missing-deadline state |
| POST /internal/v1/ocr/extract | Scoped receipt bytes, declared content type, source digest, job ID | Extracted fields, per-field confidence when available, source digest and adapter version | Manual entry available. Failed extraction retains the original and creates no verified amount. |

For JSON interfaces use explicit request and response models, documented field lengths/types and an error envelope with a stable code, readable message, field errors and request ID. Validate unknown fields at command boundaries. Use 401 for an unauthenticated API client, 403 for a known forbidden action, 404 for a concealed out-of-scope object, 409 for a current-state conflict and 422 for invalid structured input. Django can re-render invalid forms with field errors and redirect unauthenticated browser traffic to sign-in. Use 202 only for a durably accepted job. Configure finite timeouts, retry budgets and upload limits per adapter.

## 3. Data contracts and constraints

Use stable identifiers and foreign keys for all business records. Keep an explicit revision counter on mutable drafts and current aggregate rows. Use protected foreign keys on referenced history. Store monetary amounts as PostgreSQL NUMERIC and Python Decimal, with an explicit currency. Use time-zone-aware instants for events and decisions. Interpret local opening hours and working-day rules in Asia/Dhaka before constructing instants.

| Record family | Required relationships and invariants |
|---|---|
| Account, assignment, grant, profile change | Unique normalized IUB address, unique verified provider issuer/subject binding, active flag, separate personal contacts. Assignment references person, role, optional club and term, inclusive policy dates and granting actor. A typed designation is descriptive. A profile request stores field, original, proposed, decision and reviewer. |
| Club, EB term, membership, handover | One club per term, validated term boundaries, effective appointments and configurable posts. Handover links outgoing and incoming terms plus permitted unfinished work. Preserve original authors and terms. |
| Policy, template, event, event version | Policy versions carry effective dates and issuer. Templates carry labeled fields, required evidence and two signature stages. Each event version links to one club or DoSA owner, organizer, schedule and applicable approval records. Keep current approved and proposed revisions separate. |
| Memo, submitted version, decision, signature | A memo carries its event/template references. A submitted version freezes content, attachment references, budget version and applicable policy. Enforce at most one final decision per version/stage. A signature records authenticated signer, stage, version, attestation and timestamp. Keep EB handoff, DoSA queue entry, approval deadline and event start separate. |
| Venue, restriction, booking request, reservation | Store opening rules, central events/closures, buffers, capacity and permitted use. A reservation has a venue and an occupied time range linked to the confirmed booking. A replacement request references the original booking. |
| Funding period, allocation, release, expense, budget, adjustment | Every entry has scope, currency and source. Evidence and expense decisions bind to expense revisions. A confirmed release records actual date, amount and evidence/reference. Use directed adjustments with an eligible source and unique operation key. |
| Publication, attempt, event outcome, report | One publication identity per event/destination, with approved version, state, external reference and last confirmed synchronization. Store attendance, achievements, measurement basis and term. Reports reference contributing source revisions, extraction time, filters and currency. |
| File, import, audit, outbox, command receipt | Files carry record and immutable content identity. Imports retain origin, author when known, verification status and source identity. Audit carries actor, effective role, object, revision, change, reason and time. One durable job per intended side effect. Command receipts link a replay to its prior outcome. |

Index foreign keys and frequently filtered combinations, including club and term, event and status, memo stage and deadline, ledger scope and period, and runnable job state and next-attempt time. Verify indexes against the pilot dataset with query plans. Avoid redundant totals tables until a measured need justifies caching.

## 4. Authority, identity and evidence

1. Register a server-side Google OpenID Connect client. Validate signature against the provider’s keys, issuer, audience, expiry, state and nonce as applicable. Require verified institutional email and the IUB-approved hosted domain. Match the first sign-in to one provisioned active profile, then bind the stable issuer and subject. Handle a later address change through authorized review. A client-supplied email suffix is insufficient evidence of institutional identity.
2. Bootstrap the first System Admin through an operator-only, idempotent management command bound to a named IUB identity. Audit execution. The System Admin then provisions the initial DoSA Head. Keep production sign-in on the same verified institutional path. Do not ship seeded production passwords or a development bypass.
3. Authorize with the current actor, action, record owner, effective assignment, term and grant. For sensitive writes, serialize changes to the relevant authority records with a documented lock order. Re-read effective authority before committing. Recheck access when serving generated downloads. Show only the permitted modules in navigation and the same permitted records in searches, totals and counts.
4. Rotate the session on sign-in, invalidate it on logout and reject inactive or expired assignments on every protected operation. Use secure, HTTP-only session cookies, appropriate SameSite settings, HTTPS and CSRF protection for browser writes. Keep tokens, raw contact details, receipts and signature images out of logs. Production settings restrict hosts and trusted origins and disable debug pages.
5. Stage uploads privately under generated keys, validate actual content type and size, and record their digest before accepting them as evidence. Keep rejected or quarantined files inaccessible. Tie previews and downloads to a fresh authorization check. Expire unused staged uploads after the configured retention window. A failed new upload preserves accepted earlier evidence.
6. Expose ordinary profile change notices to active DoSA personnel as specified in FR-IAM-05. Put only the request reference in notifications when the actual field is sensitive. Limit the details to the appropriate review context. An IUB sign-in address, scope or grant change follows the privileged account-management path.

Identity and deployment references: [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect) · [Django deployment checklist](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/).

## 5. Transactions and lifecycle commands

**Command protocol.** Accept a stable operation key plus expected object revision. Within one Django atomic transaction, enforce current scope, claim the key under a unique actor/action/key constraint, lock affected records in consistent order, compare revisions, validate policy, save all records, append audit and enqueue side effects. Store a hash of the semantic payload and result reference. An authorized replay with the same payload returns the recorded result. Reuse with different content returns a conflict. Recheck current access before disclosing a stored result. Handle an integrity error outside the failed transaction or within an explicit savepoint.

**Memo.** Saving a draft may omit fields. Submission requires the applicable links, mandatory fields, evidence and assigned reviewer. Freeze the version during both review stages. Advisor confirmation and Head approval each validate and bind the appropriate e-signature to that exact version. Rejection requires a reason and routes to the EB. At the Head stage it also notifies the Advisor. Keep rejected and withdrawn versions immutable. A revision or amendment makes a new reviewable version with fresh signatures. Preserve the previous approved version until the amendment clears its gates.

**Reservation.** Represent effective occupancy as a nonempty half-open timestamp range [start minus setup, end plus cleanup). Use a PostgreSQL GiST exclusion constraint over equal venue ID and overlapping effective ranges for active reservations, with btree_gist for scalar equality as needed. Lock the venue row for both confirmation and changes to its rules/closures. Re-read applicable policy, central events, approvals, hours, capacity and current reservations while holding that lock. A request or AI suggestion does not hold a slot. For a move, lock both venues in stable ID order, release old occupancy and insert the new reservation within one transaction. An insert conflict rolls the entire move back. Use the same lock discipline for venue-rule updates. Flag affected existing confirmations for authorized resolution instead of silently removing them.

**Lifecycle dependencies.** Approval-sensitive event edits create proposed revisions. Keep event status, memo decision, reservation and publication state visible independently. An event cancellation records its reason, closes active requests, releases occupancy, changes the internal calendar and updates or withdraws the internal notice atomically. Enqueue any external withdrawal in that transaction. Preserve prior decisions, finance and evidence. For a reschedule, switch the current approved event and eligible internal notice only after the linked approvals and venue swap succeed.

**Finance.** Lock the expense or release being decided. Store revisions, review decisions, adjustments and their effects in one transaction. Reject duplicate correction operations. Keep allocations, release schedules, actual confirmed releases and bank movements distinct. Verified event expenditure is the sum of verified amounts and accepted signed adjustments. Event net cash flow uses only confirmed inflows attributed to that event. Budget variance equals verified expenditure minus the selected planned budget. Separate currencies unless an explicit conversion record provides rate and effective date.

**Reconciliation fixture.** In a single BDT period, allocate 10,000 to Club A, schedule 4,000, confirm 3,500 actually released, and attribute 2,000 of that inflow to Event E. Verify an expense of 800, then apply a linked reduction of 50. With no other entries, the expected club balance is 2,750 and event net cash flow is 1,250. Against a planned event budget of 900 the variance is −150. A repeated adjustment, an unverified receipt and another club’s release leave these three figures unchanged.

**Handover and imports.** Close or date outgoing appointments and register successors atomically. Preserve historical term IDs when granting responsibility for unfinished work. Validate historical imports against stable source identities and references, retaining provenance. A historical-only row cannot establish a past live approval, payment verification or reservation.

Database references: [Django transactions](https://docs.djangoproject.com/en/5.2/topics/db/transactions/) · [PostgreSQL ranges and exclusion constraints](https://www.postgresql.org/docs/current/rangetypes.html).

## 6. Integration failures and recovery

| Integration | Runtime rule | Acceptance test |
|---|---|---|
| Google sign-in | If the provider is unavailable or returns an unverifiable result, leave the user signed out and allow a new sign-in attempt. | Cancel sign-in, use an inactive profile and expire an assertion. No session is created. |
| IUB email | Enqueue one notification per business event, intended recipient and channel. Store attempts, provider reference and last outcome. Keep in-app entries visible after email failure. | Advisor rejects: EB receives the in-app notice and IUB email, Head sees tracking and receives no rejection email. Head rejects: EB and Advisor receive the required notices. |
| OCR | Attach output to the original digest and expense version. Label extracted fields unverified. Human review accepts or edits fields before finance verification. Duplicate hints are advisory. | Deliver a late OCR result after an expense revision. Earlier output remains traceable and cannot overwrite reviewed fields. |
| Scheduling | Django filters candidates against hard rules. FastAPI ranks eligible candidates using permitted preference features or an approved provider. Django validates returned IDs and rechecks live availability at submission and confirmation. | Timeout, invalid candidate, stale availability and empty set all leave manual search available. |
| Priority | Derive actionable rows from pending Head decisions. Compute time to deadline from the configured calendar. Separate past event dates and insufficient lead times. Track inputs, ranking time and expiring manual overrides. | Change one deadline and expire an override. Verify new order, explanations and earliest-deadline fallback. Missing deadlines remain labeled and visible. |
| External publishing | Build a destination-specific allowlisted payload from an approved event version. Validate eligibility on send. Serialize operations per event/destination and discard obsolete pending sends. | Let an old update arrive after cancellation. Reconcile to the latest authorized state and avoid a second notice. |
| Reports and exports | Freeze the filter, source revision basis, scope, currency, verification policy and extraction time. Recheck permission at generation and retrieval. | Contact fields, bill links and records outside the authorized export are absent. Handle zero rows, revoked scope and failed generation explicitly. |

Use job states queued, leased, succeeded, retryable, failed and uncertain as applicable. Claim a bounded batch with a lease, release locks before network I/O and recover expired leases. Use bounded backoff, an attempt limit and a visible retry action. Propagate operation IDs to providers supporting idempotency. A timeout after a remote write may mean the provider already acted. Check its reference or reconcile the destination first. If its interface cannot establish the outcome, mark uncertain for operator review. The application guarantees a single business decision and durable notification intent. It should never promise exactly-once email delivery over a provider without that guarantee.

## 7. Build, test and run

- **Local setup.** Provide a locked dependency file, environment example with placeholders, documented Python and PostgreSQL versions, and a reproducible local service definition. Declare compatible version ranges, pin the resolved versions in the lock and exercise that same set in CI. Document installation, database creation, migration, synthetic fixtures, web/worker/assistance startup and tests. Keep development accounts, provider fakes and test credentials isolated from production.
- **TDD.** Start each change with one failing behavioral test linked to an FR or UC, show it fails for the intended reason, implement the minimum path and refactor under green tests. Add applicable denial, stale state, duplicate, rollback and provider-failure tests before completing the slice. Use a controlled clock, private temporary file store and fake providers for deterministic cases.
- **Test layers.** Unit-test arithmetic and policy. Test Django commands/forms and FastAPI request/response validation independently. Test the real Django-to-FastAPI contract through an HTTP test server. Use actual PostgreSQL transactions and separate connections for booking, finance and memo races. Drive the deployed application with a browser for primary user journeys. Keep a separate opt-in staging smoke test for each configured live integration.
- **CI.** On an empty PostgreSQL service install from the lock, lint and format-check, run system checks, check for uncommitted migrations, migrate, run all unit/integration/browser tests and reconcile acceptance markers to PRD IDs. On schema changes also upgrade a representative earlier dataset. Fail the pipeline on failed checks. Report skipped provider smoke tests separately.
- **Deployment.** Use separate application and migration database credentials, restricted network access and encrypted transport for sensitive traffic. Perform database and file backup before significant migrations. Apply compatible additive migrations before switching app/worker versions. For a breaking migration, stage the backfill and validate pre/post counts before removing the old representation. Rehearse rollback or forward recovery on staging.
- **Operations.** Provide health probes for web, database readiness, worker heartbeat and assistance availability. Record correlation ID, command code, elapsed time, outcome and safe aggregate IDs. Monitor decision errors, conflict rates, job backlog/age, unavailable original files and provider timeouts. Assistance failure must degrade only the dependent functionality.
- **Recovery.** Back up PostgreSQL and immutable file objects on a coordinated basis. Keep a manifest with file digests. Restore into an isolated environment with outbound sends disabled, verify database references, financial totals, signatures, active reservations and sample file checksums. Reconcile pending outbox work before enabling delivery. Record actual recovery time and data loss against the institution’s agreed objectives.
